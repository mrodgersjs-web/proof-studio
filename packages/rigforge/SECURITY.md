# Security

## The limitation you need to know first

**RIGForge's seal is symmetric. A third party cannot verify your ProofPacket.**

The signature is `HMAC-SHA256(signing_key, packet_sha256)`. HMAC uses one secret
for both signing and verifying, so anyone who can *check* a packet can also
*forge* one. There is no public key and no public verifiability. Concretely:

- You cannot publish a ProofPacket and let a stranger confirm it is genuine —
  handing them the key to verify also hands them the ability to mint proofs.
- The claim RIGForge supports is **"this packet has not been altered since *we*
  sealed it, and it was sealed by a holder of *our* key."** It is not
  "this packet is provably attributable to a specific party" in any sense a
  neutral observer could check.
- `packet_sha256` on its own proves nothing about origin. It is a plain SHA-256
  over the canonical packet JSON, so anyone who edits a packet can recompute it.
  The HMAC is the only thing standing between a tampered packet and acceptance —
  which is why `verify --require-signature` matters and a bare hash check does
  not.

**If you need a third party to verify independently, RIGForge is the wrong
layer.** Use asymmetric signing:

- [**Sigstore**](https://www.sigstore.dev/) (`cosign`) — keyless signing with
  short-lived certificates and a public transparency log. The usual choice when
  arbitrary downstream consumers must verify artifacts.
- [**in-toto**](https://in-toto.io/) — signed attestations about *supply-chain
  steps*, which is much closer to what a ProofPacket is conceptually. If you want
  RIGForge's model with public verifiability, in-toto attestations (optionally
  carried via [SLSA](https://slsa.dev/) provenance) are the mature path.

Wrapping a ProofPacket in a sigstore/in-toto attestation is a legitimate
composition: RIGForge decides *what is true about the run*, the attestation layer
makes that decision *publicly checkable*. RIGForge does not do the second half
today, and does not claim to.

## What is actually guaranteed

| Property | Mechanism | Holds against |
|---|---|---|
| Integrity | `packet_sha256` = SHA-256 over canonical packet JSON (sorted keys, hash/signature fields excluded) | Accidental corruption |
| Authenticity | `HMAC-SHA256(key, packet_sha256)`, compared with `hmac.compare_digest` | An attacker **without** the signing key |
| Nothing | — | An attacker **with** the signing key |

Because the HMAC covers `packet_sha256`, and that hash covers the artifacts,
gates, spec binding and run envelope, tampering with any of those invalidates the
signature. That chain is the whole security argument, and it is only as strong as
the secrecy of the key.

For the full trust boundaries — including what RIGForge deliberately does *not*
defend against (a compromised key, an agent that simply never seals, malicious
code that passes honest gates, weak gates) — see
[`docs/THREAT_MODEL.md`](docs/THREAT_MODEL.md).

## Key handling

The signing key is 32 random bytes, hex-encoded, generated by `rigforge init` at
`.rigforge/signing.key` with `0600` permissions. `.rigforge/` is in
`.gitignore`. Resolution order:

1. `RIGFORGE_SIGNING_KEY` (the key value itself)
2. `RIGFORGE_SIGNING_KEY_FILE` (path to the key)
3. `signing.key_file` in `rigforge.yaml`
4. `.rigforge/signing.key`

Two practical cautions:

- **Prefer the `_FILE` form over `RIGFORGE_SIGNING_KEY`.** A raw key in an
  environment variable is visible to child processes and tends to end up in CI
  logs, crash dumps, and `ps` output.
- **Keep the key off the machine running the agent.** The agent is the adversary
  in this threat model. If it can read the key, it can seal whatever it likes and
  RIGForge tells you nothing useful. A CI-only key the agent never sees is the
  intended deployment.

The MCP/cockpit server has a separate secret, `RIGFORGE_MCP_TOKEN` (bearer-token
auth). It is unrelated to proof signing and does not grant the ability to seal.

## Reporting a vulnerability

Email **security@rodgersintelligence.com**. Please do not open a public issue for
anything that would let someone forge a packet that
`rigforge verify --require-signature` accepts.

Useful to include: the version or commit, a minimal reproduction, and what an
attacker gains. A working forgery is the strongest possible report — the
`rigforge benchmark` forgery suite is a good place to express it as a new
scenario.

This is a single-maintainer project, not a funded security program. There is no
bounty and no guaranteed response SLA. What is promised: a real reply rather than
silence, and credit in the fix unless you prefer otherwise.

## Supported versions

Only the latest release on `main` receives fixes. There are no maintained release
branches.

# Architecture

## One-liner

proof-studio authors tamper scenarios and runs them against the real rigforge
verifier; rigforge (vendored under `packages/rigforge`) is the core library that
seals and verifies ProofPackets.

## Flow

```text
scenarios.yml  ->  vector JSON (ProofPacket)  ->  strict verify  ->  per-class report
                                                      |
                            integrity + HMAC signature + claim binding
```

## Components

| Module | Responsibility |
| --- | --- |
| `proof_studio/scenarios.py` | `Scenario` rows, manifest loading and validation, deterministic vector builders, the demo signing key |
| `proof_studio/runner.py` | The strict verify policy, `ScenarioResult`, `summarize` rate math |
| `proof_studio/report.py` | Text table and JSON report rendering |
| `proof_studio/cli.py` | `proof-studio run`, `list`, `build-vectors` |
| `proof_studio/_vendor.py` | Resolves `import rigforge` to `packages/rigforge` from a repo clone |

## The strict verify policy

A packet is accepted only when all three pass:

1. **Integrity** (`ProofPacket.verify_integrity`): the packet hash matches its content.
2. **HMAC signature** (`ProofPacket.verify_signature` with the demo key): the
   packet hash is signed by the key holder. A tamper that re-forges the packet
   hash passes (1) and fails here.
3. **Claim binding** (`ProofPacket.matches_claim`): the packet was sealed for the
   claim being verified (phase and name are inside the signed hash). A replayed
   valid packet passes (1) and (2) and fails here.

## Vector lifecycle

- Vectors are generated by `proof-studio build-vectors` from builders in
  `scenarios.py`. Builders use fixed timestamps and fixed artifact bytes, so
  regeneration is byte-identical and the committed files are reproducible
  (asserted by `tests/test_cli.py`).
- `tests/failures/scenarios.yml` binds each vector to the claim it is submitted
  against and the verdict the verifier must reach.
- `proof-studio run` exits 1 on any expectation mismatch, which is how a planted
  failure that stops going red fails CI.

## Outcome classification

`ScenarioResult.outcome` compares what the vector really is (`kind`) with what
the verifier did, so a regression reads `missed_forgery` even if a manifest row
is mislabelled:

| kind | verifier says accept | verifier says reject |
| --- | --- | --- |
| control | `clean` | `wrongly_blocked` |
| any forgery | `missed_forgery` | `caught` |

## Trust boundaries

- Public inputs only: vectors, manifest, demo key are repo files. The demo key is
  derived from a literal string and is not a secret.
- Secrets never enter the repo. Real deployments keep signing keys outside it
  (see `docs/public-boundary.md`).
- The strict policy is a verification policy only; nothing here executes an
  outward action. The optional `mcp/server.py` surfaces verified results and
  records Gate-D requests without executing them.

## Relationship to rigforge

rigforge ships its own seeded benchmark (`rigforge benchmark`) for the core
library. This studio is the layer around it: authorable scenarios, committed
planted-failure vectors, per-class catch reports, and a CI gate over the
verifier's behavior. Feature work on sealing, verification and claim binding
belongs in the rigforge repo; scenario authoring and catch reporting belong here.
